Трекер задач, который проходит через всю карту [Go Backend Roadmap](https://ubicasmerti228.github.io/go-roadmap/). Каждая версия проекта закрывает чек-лист своего этапа и помечена тегом.

Сначала сделай версию сам, потом сравни с этой. Совпадать не обязано: здесь один из разумных вариантов, а не единственно верный.

## Запуск

Нужен Docker.

```
cp .env.example .env      # поменяй пароли и JWT_SECRET
make up                   # два сервиса, PostgreSQL, Redis, Kafka, Prometheus и Grafana
make smoke                # главный путь пользователя, включая уведомление через Kafka: нужны curl и jq
make observe              # метрики собираются, дашборд не пустой
make down
```

Kafka — самая тяжёлая часть стенда: первый запуск скачивает образы несколько минут.

Руками:

```
curl -X POST -d '{"email":"ann@example.com","password":"correct horse"}' localhost:8080/api/v1/auth/register
curl -X POST -d '{"email":"ann@example.com","password":"correct horse"}' localhost:8080/api/v1/auth/login
# подставь access_token из ответа
curl -H 'Authorization: Bearer <токен>' -X POST -d '{"title":"сдать отчёт"}' localhost:8080/api/v1/tasks
curl -H 'Authorization: Bearer <токен>' 'localhost:8080/api/v1/tasks?limit=10'
curl -H 'Authorization: Bearer <токен>' localhost:8080/api/v1/notifications   # через секунду-другую после создания задачи
```

Что ещё открыто на твоей машине:

## v1.0 — два сервиса

Появился второй сервис, notifier: он превращает события задач в уведомления и отдаёт их по gRPC. Сервисы общаются двумя способами — асинхронно через Kafka и синхронно через gRPC.

### Путь одного уведомления

1. `POST /api/v1/tasks`. TaskFlow одной транзакцией пишет задачу и событие `task.created` в таблицу `outbox`.
2. Relay раз в секунду переносит новые события из `outbox` в топик Kafka `taskflow.tasks`.
3. notifier читает топик и одной транзакцией сохраняет уведомление и отметку «событие обработано».
4. `GET /api/v1/notifications`. TaskFlow запрашивает уведомления у notifier по gRPC и отдаёт их клиенту.

Так же идёт событие `task.due`: воркер напоминаний записывает его вместе с отметкой о напоминании.

### Чек-лист этапа

| Пункт | Где смотреть |
|-------|--------------|
| Сервис notifier с gRPC API и proto-контрактом | `proto/taskflow/notifier/v1/notifier.proto`, `internal/notifier/grpcserver`, `cmd/notifier`; клиент — `internal/notifierclient` |
| TaskFlow публикует TaskCreated в Kafka через outbox | `Create` в `internal/postgres/tasks.go`, `internal/postgres/outbox.go`, `internal/outbox/relay.go`, `internal/kafka/producer.go` |

### Наблюдаемость

У каждого сервиса два порта. Публичный (8080 у TaskFlow, 9000 у notifier) обслуживает запросы. Служебный (8081 и 9001) отдаёт `/metrics` и `/debug/pprof/`; в compose он не опубликован, до него достаёт только Prometheus.

Дашборд построен по методу RED: частота запросов, доля ошибок, время ответа. К ним добавлены очередь outbox, события notifier, горутины и память. У каждой панели есть описание — наведи на значок «i».

Снять профиль со своей машины: временно добавь `- "127.0.0.1:8081:8081"` в `ports` сервиса `api`, перезапусти его и выполни

```
go tool pprof -http=:7000 'http://localhost:8081/debug/pprof/profile?seconds=30'   # CPU, под нагрузкой
go tool pprof -http=:7000 http://localhost:8081/debug/pprof/heap                   # память
```

Посмотреть на отказоустойчивость:

```
docker compose stop kafka      # задачи создаются, на дашборде растёт «Outbox: событий в очереди»
docker compose start kafka     # очередь уходит в ноль, уведомления появляются
docker compose stop notifier   # /api/v1/notifications отвечает 503, задачи работают
```

### Решения и компромиссы

**События**

- **Событие пишется в базу, а не сразу в Kafka.** Запись в базу и отправка в брокер — две разные системы, и одна из двух операций может не пройти: задача есть, события нет, или наоборот. Таблица `outbox` сводит это к одной транзакции. Цена — задержка до секунды и ещё один фоновый процесс.
- **Доставка «хотя бы один раз» на каждом участке.** Relay может отправить событие дважды, если не прошёл коммит после публикации. Читатель может получить его дважды, если упал между обработкой и подтверждением offset. Поэтому notifier запоминает id обработанных событий и повтор пропускает.
- **Идентификатор события строится из данных, а не случайный:** `task.created:17`, `task.due:17:<срок>`. Повторная запись того же события в outbox ничего не добавляет.
- **Порядок гарантирован только для событий одной задачи.** Ключ сообщения — id задачи, поэтому её события лежат в одной партиции. Между разными задачами порядка нет.
- **Публикует один экземпляр TaskFlow за раз** — под advisory-блокировкой PostgreSQL. Иначе два экземпляра отправили бы события не по порядку. На время публикации в базе открыта транзакция, не дольше 10 секунд.
- **Relay опрашивает таблицу раз в секунду.** Это просто, но на пустой очереди запросы идут впустую. Альтернативы — `LISTEN/NOTIFY` или чтение журнала базы (Debezium).
- **Опубликованные строки outbox не удаляются.** В рабочей системе их чистят по расписанию.
- **События — JSON, а не protobuf.** Их можно прочитать консольным клиентом Kafka. Схема описана Go-структурой в `internal/event`; реестра схем нет. Незнакомые поля и незнакомые типы событий читатель пропускает: издателя можно обновлять раньше читателя.
- **Битое сообщение пропускается с записью в лог.** Отдельного топика для таких сообщений (dead letter queue) нет.
- **Сбой обработки останавливает партицию.** Обработчик повторяется с растущей паузой, пока не справится: иначе нарушился бы порядок. Если база notifier лежит, события ждут в Kafka. Отставание читателя (consumer lag) здесь не измеряется — в рабочей системе на него ставят алерт.
- **Топик создают сами сервисы, с тремя партициями.** Автосоздание в брокере выключено: оно дало бы одну партицию, а менять их число у работающего топика нельзя без нарушения порядка.
- **Kafka в compose — один узел.** `acks=all` при одной реплике не защищает от потери диска.
- **Напоминания теперь двух видов.** Событие `task.due` уходит в notifier надёжно, через outbox. Вебхук из v0.5 остался отдельным каналом с прежними свойствами.

**gRPC**

- **Соединение между сервисами без TLS и без аутентификации.** notifier верит `user_id`, который прислал TaskFlow: проверка токена остаётся на стороне TaskFlow. Защита — только то, что порт notifier закрыт снаружи. В сети, которой нельзя доверять, нужен mTLS.
- **На каждый вызов клиент ставит deadline** (2 секунды) и держит circuit breaker из v0.5. Если notifier не отвечает, `/api/v1/notifications` возвращает 503, а остальное API работает.
- **Kafka и notifier не входят в `/readyz` TaskFlow.** Без них сервис продолжает принимать задачи; если бы они входили, падение соседа выводило бы из балансировки и его.
- **REST перед gRPC написан руками** — метод один. grpc-gateway оправдан, когда методов десятки.
- **Идентификатор запроса едет в метаданных gRPC** и попадает в логи notifier: по `request_id` находится вся цепочка. Через Kafka он не передаётся, трассировки (OpenTelemetry) нет.
- **Стрим раздаёт уведомления только своего экземпляра notifier.** Подписки хранятся в памяти процесса. С несколькими экземплярами подписчик видел бы лишь часть событий; понадобился бы общий канал, например Redis pub/sub.
- **Медленный подписчик стрима отключается** с кодом `ResourceExhausted`: сервер не копит для него уведомления без конца.
- **Клиенту уходит `Internal` без подробностей,** причина остаётся в логе notifier.

**Хранение и сборка**

- **У notifier своя схема в той же базе, а не своя база.** Так стенд проще, и существующий том PostgreSQL не нужно пересоздавать. Сервисы не читают таблицы друг друга; в рабочей системе базы были бы раздельными.
- **Оба сервиса живут в одном репозитории и одном Go-модуле** и делят пакеты: `internal/event`, `internal/resilience`, `internal/server`. Контракт между ними — `.proto` и формат событий. Цена: сервисы нельзя выпустить с разными версиями общих пакетов.
- **Образ TaskFlow вырос с 27 до 36 МБ:** добавились gRPC, клиент Kafka и клиент Prometheus. Образ notifier — 25 МБ. CI держит порог 45 МБ, чтобы рост не прошёл незаметно.
- **Сгенерированный код лежит в репозитории.** Проект собирается без buf и плагинов; CI проверяет, что код соответствует `.proto`.

**Наблюдаемость**

- **Метрики и pprof отдаются без аутентификации.** Их защищает только то, что служебный порт не опубликован.
- **В метках метрик — шаблон маршрута, а не путь.** Несуществующие пути сведены к одному значению `unmatched`. Идентификаторов пользователей и задач в метках нет: каждое новое значение метки — новый временной ряд.
- **Границы корзин гистограмм — от 1 мс до 5 с.** Перцентиль считается по корзинам, поэтому он приблизительный.
- **Алертов нет:** дашборд показывает, но не будит.

```

**Интерфейс у потребителя.** Воркер напоминаний объявляет у себя `Notifier` с одним методом. В v0.4 его реализовывал логгер, теперь — клиент вебхуков. Воркер при этом не изменился ни на строку: какая реализация придёт, решает `main`.

**Декоратор.** `instrument.Tasks` оборачивает хранилище задач и возвращает тот же интерфейс. Сервис не знает про обёртку, PostgreSQL-репозиторий не знает про логи. Обёртка проходит тот же набор тестов, что и само хранилище.

**Вебхук.** Задай `WEBHOOK_URL`, и напоминания пойдут POST-запросом на этот адрес:

```
POST <WEBHOOK_URL>
Content-Type: application/json
X-Taskflow-Event-Id: task.due:17:1777629600
X-Taskflow-Signature: sha256=<HMAC-SHA256 тела с ключом WEBHOOK_SECRET>

{"event":"task.due","task_id":17,"title":"сдать отчёт","due_at":"2026-05-01T10:00:00Z"}
```

Без `WEBHOOK_URL` напоминания по-прежнему пишутся в лог. Весь путь — отказы получателя, повторная отправка, проверка подписи — проходит тест `TestRunServiceWebhook` в `cmd/taskflow/main_test.go`.

### Решения и компромиссы

- **Retry и breaker написаны руками, без библиотек.** Это 200 строк, и цель репозитория — показать, как они устроены. В рабочем проекте разумно взять готовое: `sony/gobreaker`, `cenkalti/backoff`.
- **Повторяются только временные отказы:** обрыв сети, таймаут, статусы 408, 429 и 5xx. Ответ 4xx означает, что запрос неверен, и повтор даст то же самое.
- **Пауза между попытками случайная** (full jitter): от нуля до потолка, который удваивается. Без случайности все клиенты, упавшие одновременно, повторили бы запрос одной волной.
- **Breaker считает отказы подряд, а не долю за окно.** Это проще, но при редких запросах он размыкается медленно, а один случайный успех обнуляет счётчик. Отказ 4xx он сбоем не считает: получатель жив.
- **Доставка «хотя бы один раз».** Отметка о напоминании ставится после ответа 2xx. Если ответ потерялся, событие уйдёт повторно, поэтому у всех попыток один `X-Taskflow-Event-Id` — получатель отбрасывает дубликаты по нему.
- **Очереди неотправленных событий нет.** Пока получатель лежит, задача остаётся без отметки и берётся в каждый обход воркера; breaker делает такие попытки мгновенными. Если получатель не поднимется, напоминание так и не уйдёт, а о проблеме скажут только предупреждения в логе. Надёжная доставка через очередь появится в v1.0.
- **Адрес вебхука берётся только из настроек.** Пользователь не может его задать, поэтому заставить сервис ходить по внутренним адресам (SSRF) нельзя. По той же причине клиент не выполняет перенаправления.
- **Подпись защищает от подделки, но не от повтора:** перехваченный запрос можно отправить ещё раз. Получателю стоит помнить обработанные `X-Taskflow-Event-Id`.
- **Декоратор пишет в лог, метрик пока нет.** Обычный вызов — уровень debug, медленнее `SLOW_QUERY` — warn, сбой — error. «Не найдено» и отмена запроса клиентом сбоем не считаются.
- **Опции вместо структуры настроек — там, где у большинства полей есть разумное значение по умолчанию.** У `httpapi.Deps` все поля обязательны, поэтому там осталась структура.
- **Оптимизация ключа кэша дала 0,4% времени запроса.** Она оставлена, потому что ничего не стоила; настоящие затраты — проверка токена. Подробности в [docs/perf.md](docs/perf.md).
- **`Shutdown` ждёт до пяти секунд соединения, по которым ещё не пришло ни одного запроса.** Поэтому `SHUTDOWN_TIMEOUT` меньше пяти секунд может закончиться ошибкой при полностью обработанных запросах.

### Деплой

Что здесь есть и что проверено:

- **Образ публикуется в GHCR** из ветки `main` после зелёных проверок, с тегом по SHA коммита и `latest`.
- **`deploy/compose.prod.yaml`** запускает образ за Caddy: наружу открыты только порты 80 и 443, сертификат Let's Encrypt Caddy получает сам. CI поднимает эту схему с доменом `localhost` и проходит по ней `smoke.sh` через HTTPS.
- **Выкатка на сервер по SSH** описана в задании `deploy`, но ни разу не запускалась: сервера у этого репозитория нет. Задание включается, когда в настройках репозитория заданы переменная `DEPLOY_HOST` и секреты `DEPLOY_USER`, `DEPLOY_SSH_KEY`.

На сервере:

```
mkdir ~/taskflow && cd ~/taskflow
# сюда нужно положить папку deploy из репозитория и файл .env с DOMAIN=твой.домен
docker compose --env-file .env -f deploy/compose.prod.yaml up -d
```

Откат — запуск предыдущего тега: `TAG=<sha> docker compose --env-file .env -f deploy/compose.prod.yaml up -d`.

### Решения и компромиссы

- **Проверка входных данных разделена.** Формат (обязательные поля, длина, вид email) проверяет HTTP-слой тегами валидатора. Правила предметной области (заголовок не из одних пробелов, email свободен) — сервис. Ограничения в базе остаются последней линией защиты.
- **Чужая задача отвечает 404, а не 403.** Владелец входит в условие каждого запроса к базе и в ключ кэша, поэтому по ответу нельзя узнать, существует ли задача с таким id.
- **Refresh-токен — случайная строка, а не JWT.** На сервере лежит его хеш с временем жизни. Токен одноразовый: при обмене старый удаляется одной командой `GETDEL`.
- **Access-токен нельзя отозвать до истечения 15 минут.** Это цена проверки без обращения к хранилищу. Чёрного списка токенов нет.
- **Вход отвечает одинаково на неверный email и неверный пароль** и тратит на них одинаковое время: для неизвестного email пароль сравнивается с заготовленным хешем.
- **Кэшируется только чтение одной задачи.** Списки не кэшируются: фильтров много, а сбрасывать их пришлось бы при каждом изменении.
- **Недоступный Redis не ломает работу с задачами:** сервис пишет предупреждение и идёт в базу. Вход и обновление токенов без Redis не работают, поэтому `/readyz` отвечает 503.
- **Ограничение частоты входа — фиксированное окно** в минуту на IP. На границе окон оно пропускает до двойной нормы. При недоступном Redis ограничение отключается, а не блокирует вход.
- **За прокси сервис верит заголовку `X-Forwarded-For` только от адресов из `TRUSTED_PROXIES`.** Иначе клиент подставил бы любой IP и обошёл ограничение частоты.
- **CLI-команды add, list и done убраны.** У задач появились владельцы, а входа из консоли нет.
- **Пользователь `demo@taskflow.local` из v0.3 остаётся в базе без пароля:** войти под ним нельзя, его задачи недоступны через API.
- **Gin увеличил бинарник примерно вдвое** по сравнению с v0.3. Тег сборки `nomsgpack` убирает 6 МБ ненужного кода, образ остаётся меньше 30 МБ.
- **CORS не настроен:** у сервиса нет браузерного клиента.
- **Напоминания по-прежнему пишутся в лог.** Отдельный сервис уведомлений появится в v1.0.

### Тесты

```

Без Docker интеграционные тесты можно направить в уже запущенную базу:

```

Тесты очищают таблицу `tasks`, поэтому база должна быть отдельной, не рабочей.

### Решения и компромиссы

- **Файловое хранилище удалено, а не оставлено вторым вариантом.** Две реализации пришлось бы поддерживать в каждой следующей версии.
- **Один набор тестов проходит и хранилище в памяти, и PostgreSQL** (`tasktest.RunStoreSuite`). Поэтому тестам HTTP-слоя и CLI можно доверять, хотя базы под ними нет.
- **Все задачи принадлежат одному пользователю `demo@taskflow.local`,** его создаёт вторая миграция. Таблица `users` и внешний ключ уже есть, аутентификация появится в v0.4.
- **Миграции вшиты в бинарник и накатываются при старте `serve`.** Блокировка в базе не даёт двум экземплярам мигрировать одновременно. Цена: откат делается новой миграцией, а не командой.
- **PATCH — один запрос с COALESCE** вместо сборки SQL из кусков. Плейсхолдеры остаются плейсхолдерами при любом сочетании полей.
- **Список поддерживает и offset, и курсор `after_id`.** Курсор идёт по индексу `(user_id, id)` и не замедляется с глубиной. `total` считается отдельным запросом `count(*)`: на миллионах строк его стоит убрать.
- **У воркера частичный индекс** по сроку: в нём только задачи, которые ещё ждут напоминания.
- **Два экземпляра сервиса могут отправить одно напоминание дважды:** оба успеют прочитать задачу до отметки. Для одного экземпляра это не проблема; лечится захватом строк через `FOR UPDATE SKIP LOCKED`.
- **Время наружу отдаётся в UTC,** в каком бы часовом поясе ни работал сервер.
- **Образ собран на distroless и запускается не от root.** В нём нет оболочки: зайти внутрь через `docker exec sh` нельзя, отладка идёт по логам.

## v0.2 — REST и фоновые задачи

В этой версии задачи ещё лежали в JSON-файле. Пути ниже относятся к тегу `v0.2`.

```
curl -X POST -d '{"title":"сдать отчёт","due_at":"2026-05-01T10:00:00Z"}' localhost:8080/tasks

Контракт API описан в [openapi.yaml](openapi.yaml), его можно открыть в [Swagger Editor](https://editor.swagger.io/).

### Чек-лист этапа

| Пункт | Где смотреть |
|-------|--------------|
| CRUD /tasks: список с пагинацией и фильтром, создание, PATCH, DELETE | `internal/httpapi/server.go` |
| Единый JSON ошибок и правильные статусы | `fail` и `writeError` в `internal/httpapi/server.go`, тест `TestErrors` |
| `openapi.yaml` описывает все endpoint'ы | `openapi.yaml` |
| Воркер напоминаний: пул горутин, остановка через context | `internal/reminder/worker.go` |
| `go test -race` чистый | `make test` |

### Как устроено

```
cmd/taskflow        точка входа: разбор команд, запуск и остановка сервера
internal/task       задача, ошибки и хранилище в JSON-файле
internal/httpapi    HTTP-обработчики и перевод ошибок в статусы
internal/reminder   воркер напоминаний
openapi.yaml        контракт API
```

### Решения и компромиссы

- **Пагинация через offset.** Она проще, и в файловом хранилище ей нечего ускорять. Keyset-пагинация появится вместе с PostgreSQL: там она опирается на индекс.
- **Ошибки превращаются в статусы в одном месте,** в методе `fail`. Хранилище возвращает `ErrNotFound`, `ErrEmptyTitle`, `ErrEmptyPatch` и ничего не знает про HTTP.
- **404 и 405 тоже приходят в общем формате.** Для этого зарегистрированы шаблоны без метода: стандартный роутер иначе ответил бы обычным текстом.
- **Воркер ждёт, пока обработается вся пачка, и только потом ищет задачи снова.** Так одна задача не уходит в работу дважды, хотя отметка о напоминании ставится после отправки.
- **Напоминание отправляется хотя бы один раз, но не ровно один.** Если программа упадёт между отправкой и отметкой, после перезапуска оно уйдёт повторно.
- **Упавшая отправка не отмечается** и повторяется на следующем обходе, без задержек и ограничения числа попыток. Повторы с растущей паузой — тема этапа 5.
- **Срок нельзя убрать через PATCH,** только заменить: `null` в JSON неотличим от отсутствующего поля без отдельного типа.
- **Остановка идёт по порядку:** сервер перестаёт принимать запросы и дожидается текущих, затем дожидается воркер.

## v0.1 — CLI и HTTP на stdlib

Решения первой версии. Первые два и последнее относятся к файловому хранилищу и ушли вместе с ним в v0.3, остальные действуют до сих пор:

- **Файл перечитывается и перезаписывается на каждую операцию.** Просто и надёжно для десятков задач, медленно для тысяч. На этапе 3 хранилище переезжает в PostgreSQL.
- **Запись идёт через временный файл и переименование.** Если программа упадёт посреди записи, старый файл останется целым.
- **Интерфейсы хранилища объявлены у потребителей** — в пакетах `httpapi` и `reminder`. Каждому нужна своя часть методов, и в тестах её легко подменить.
- **Текст внутренней ошибки не уходит клиенту.** В ответе — «internal error», подробности — в логе.
- **Логика команд вынесена из `main` в `run`.** Так CLI тестируется без запуска процесса.
- **Мьютекс защищает от гонок внутри одного процесса,** но не от двух процессов сразу: CLI и сервер, запущенные одновременно, могут перезаписать изменения друг друга.
