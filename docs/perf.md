# Замеры горячего пути

Горячий путь сервиса — чтение одной задачи: `GET /api/v1/tasks/{id}`. Он вызывается чаще всего и почти всегда отвечает из кэша.

Здесь записано, что измерено, что это показало и что из этого сделано. Числа получены на Intel Core i3-10100F, Go 1.27, Linux; на другой машине они будут другими, важны соотношения.

## Как повторить

```
make bench                                                              # все бенчмарки
go test -bench=TaskKey -benchmem -run='^$' -count=5 ./internal/service  # один, пять прогонов
go build -gcflags=-m ./internal/service 2>&1 | grep tasks.go            # что решил escape analysis
```

Один прогон ничего не доказывает: соседние запуски расходятся на несколько процентов. Сравнивать нужно серии — удобнее всего утилитой [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat).

## Три бенчмарка — три масштаба

| Бенчмарк | Что измеряет | Время | Память |
|----------|--------------|-------|--------|
| `BenchmarkTaskKey` | сборка ключа кэша | 34 нс | 16 Б, 1 аллокация |
| `BenchmarkTasksGetCached` | сервис: чтение задачи из кэша | 1,5 мкс | 120 Б, 3 аллокации |
| `BenchmarkGetTask` | весь запрос: middleware, токен, сервис, JSON | 16,7 мкс | 4,9 КБ, 69 аллокаций |

Файлы: `internal/service/tasks_bench_test.go`, `internal/httpapi/bench_test.go`.

## Что сделано: ключ кэша без fmt.Sprintf

Ключ `task:<владелец>:<id>` строится на каждое чтение. Первая версия:

```go
func taskKey(userID, id int64) string { return fmt.Sprintf("task:%d:%d", userID, id) }
```

Escape analysis (`go build -gcflags=-m`) говорит про неё:

```
tasks.go:45:74: userID escapes to heap
tasks.go:45:82: id escapes to heap
```

`Sprintf` принимает `...any`: каждое число упаковывается в интерфейс, а строка формата разбирается при каждом вызове. Новая версия собирает ключ в буфере через `strconv.AppendInt`:

```
tasks.go:50:13: make([]byte, 0, 48) does not escape
tasks.go:55:16: string(buf) escapes to heap
```

Буфер остался на стеке, в кучу уходит только готовая строка — она и должна: её возвращают наружу.

| | До | После |
|---|----|-------|
| `BenchmarkTaskKey` | 102 нс, 1 аллокация | 34 нс, 1 аллокация |
| `BenchmarkTasksGetCached` | 1,55–1,68 мкс | 1,47–1,50 мкс |

Сборка ключа ускорилась втрое. Число аллокаций не изменилось: компилятор и раньше обходился одной.

## Чего это стоит на самом деле

Втрое быстрее — это 70 наносекунд. Весь запрос занимает 16,7 мкс, то есть выигрыш — 0,4% времени запроса. А настоящий запрос ещё идёт по сети и, при промахе кэша, в базу: это сотни микросекунд и миллисекунды.

Правка оставлена, потому что она ничего не стоит: шесть строк, читаются легко. Но если бы ради неё пришлось усложнять код, делать её не стоило.

Профиль (`go test -bench=GetTask -cpuprofile cpu.prof`, затем `go tool pprof -top -cum`) показывает, куда уходит время запроса на самом деле:

| Доля времени запроса | Что |
|----------------------|-----|
| 46% | проверка access-токена: разбор JWT (два JSON-объекта) и HMAC |
| 14% | JSON-ответ |
| 12% | лог запроса |
| 12% | сервис: чтение из кэша и разбор задачи из JSON |

Вывод: оптимизировать стоило бы проверку токена, а не ключ кэша. Без профиля об этом не догадаться — поэтому сначала измеряют, потом правят.

Проверка токена здесь не ускорена: 8 мкс на запрос сервису не мешают. Если бы мешали, результат проверки можно было бы кэшировать на несколько секунд по хешу токена — ценой того, что код станет сложнее, а отзыв токена медленнее.

## Ловушка: бенчмарк измеряет сам себя

Первая версия `BenchmarkGetTask` создавала запрос внутри цикла и показывала 20,4 мкс и 10,5 КБ на операцию. Профиль памяти показал, что 47% выделенных байт приходятся на `httptest.NewRequest`: он заводит буфер чтения на 4 КБ. К сервису эта память отношения не имеет.

После выноса запроса из цикла стало 16,7 мкс и 4,9 КБ. Если результат бенчмарка удивляет, первым делом стоит посмотреть в профиль: возможно, измеряется обвязка.
